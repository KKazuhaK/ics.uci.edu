1. 基本爬取算法

第 2 周介绍了爬虫：一个像人一样点击浏览的程序，获取 HTML 页面并跟随其中的链接（第2周 §14）。在架构图中，爬取属于 文本获取（Text Acquisition） 模块（第1周 §10；L7 p3、p25 · L6.5 p12）。本周涵盖完整的算法，以及它可能出现的各种问题。

基本爬取算法（L7 p4–9，每张幻灯片逐条展示）：

  1. 初始化一个 URL 队列，即种子（seeds）。
  2. 重复以下步骤，直到队列中没有更多 URL：
    • 从队列中取出一个 URL；
    • 如果该页面允许爬取，则获取对应的页面；
    • 存储该页面的表示形式；
    • 从页面中提取 URL 并加入队列。

该队列称为待爬队列（frontier）。L7 p10–12 画出三个区域：已爬取的网页、URL 待爬队列、网络的其余部分。网络蜘蛛从种子页面出发：每次获取都会把一个页面移入“已爬取”，而它的链接则把“网络的其余部分”中的新页面拉入待爬队列。

Croft 版本的伪代码（L7 p13–15、p26 · L6.5 p13、p15 · L9 p3、p23）：

procedure CrawlerThread(frontier)
    while not frontier.done() do
        website ← frontier.nextSite()
        url ← website.nextURL()
        if website.permitsCrawl(url) then
            text ← retrieveURL(url)
            storeDocument(url, text)
            for each url in parse(text) do
                frontier.addURL(url)
            end for
        end if
        frontier.releaseSite(website)
    end while
end procedure

两项主要工作：在获得授权的前提下下载网页，并发现新的 URL（L9 p3）。L7 p14–15 重点标出了 website.permitsCrawl(url)，即你怎么知道网站是否允许爬取？（第 2 节）。待爬队列先给出一个站点，然后再从中取出一个 URL；礼貌性（politeness）就在这里体现（第 5 节）。

“爬虫眼中的网络”（L9 p4，改编自 Addison Wesley）展示了四个主机，每个主机有三个页面（www.cs.umass.edu、www.bbc.co.uk、www.whitehouse.gov、www.cnn.com），页面之间有站内和跨站的链接；还有一台机器 crawler.searchengine.com 与这四个主机通信。箭头标示 nextSite() 和 nextURL()。下面的演示会爬取这张图（幻灯片没有给出种子，我选用了 umass 和 cnn 的首页）。可以逐步查看，也可以编辑图结构后点击运行：

2. 爬取许可：robots.txt

爬取前先礼貌地询问网站是否允许你爬取（L7 p17、p19）。机器人排除标准（Robots Exclusion Standard），又称 robots.txt，是网站可以放在根目录下的一个文件（http://www.cnn.com/robots.txt、http://en.wikipedia.org/robots.txt）。它的语法非常简单，但目前“没有正式/官方标准”。它基于君子协定（honor basis）运作，它不是安全机制：忽略它的爬虫仍然能拿到页面。

五个经典示例（L7 p18 · L6.5 p16–20，来自 robotstxt.org）：

目标 robots.txt
禁止所有机器人访问整个服务器 User-agent: * / Disallow: /
允许所有机器人完全访问 User-agent: * / Disallow:（留空）
禁止所有机器人访问站点的一部分 User-agent: * / Disallow: /cgi-bin/ / Disallow: /tmp/ / Disallow: /junk/
禁止单个机器人 User-agent: BadBot / Disallow: /
允许单个机器人 User-agent: Google / Disallow: — 空行 — User-agent: * / Disallow: /

（/ 用于分隔文件中的各行。）Disallow: 后面什么都不写，表示不禁止任何内容，即“全部允许”。Disallow: / 禁止一切，因为每个路径都以 / 开头。

🗣️ 课堂上：“有一条优先级规则：如果存在专门针对某个机器人的段落，那么对该机器人适用的规则只有该段落中的规则！”（L6.5 p21）在“允许单个机器人”的例子中，Google 只读取它自己的分组（Disallow: 即全部允许），而永远看不到 * 分组中的 Disallow: /。

禁止文件夹中的允许规则（L7 p24）：你可以禁止某个文件夹，同时允许其中的一个资源，例如一个列出你希望被索引的链接的页面。CNN 的文件（L7 p21、p24）包含六行 Sitemap:、User-agent: *、若干 Allow 行，以及约 35 行 Disallow（/*.jsx$、/ads/、/aol/、/audio/、… /partners/、… /search/、… /webview/）。p24 幻灯片用方框标出了两组配对：Allow: /audio/podcasts/ 与 Disallow: /audio/，以及 Allow: /partners/ipad/live-video.json 与 Disallow: /partners/（p21 的截图中只有第二个 Allow）。

幻灯片没有解释为什么 Allow 会胜出。今天的规则（RFC 9309、Google 以及较新的 Python）是最长匹配：最长的匹配路径获胜，平局时 Allow 获胜。下面的演示把这一规则应用于 CNN 文件的节选版本：

from urllib.robotparser import RobotFileParser

rules = """User-agent: *
Allow: /audio/podcasts/
Allow: /partners/ipad/live-video.json
Disallow: /*.jsx$
Disallow: /audio/
Disallow: /partners/
"""
rp = RobotFileParser()
rp.parse(rules.splitlines())   # or set_url(...) + read()
for path in ["/audio/podcasts/ep1.mp3", "/audio/live.html",
             "/partners/ipad/live-video.json",
             "/video/player.jsx"]:
    url = "https://www.cnn.com" + path
    print(path, rp.can_fetch("MyCrawler", url))

/audio/live.html False               False

⚠️ 易错点：较旧版本 Python 的 robotparser（已测试 3.11.17 和 3.12.3；openlab 上的 3.10 更旧）会采用文件中第一条匹配的行，并且把 * 和 $ 当作字面字符。CNN 把 Allow 行放在最前面，因此只有 /*.jsx$ 会出错。但如果把 Disallow: /audio/ 放在 Allow: /audio/podcasts/ 之上，旧解析器就会阻止播客。在演示中设置 "match": "first" 即可看到这一点。

3. Sitemaps：提供给爬虫的信息

robots.txt 告诉爬虫不要去哪里。Sitemaps（由 Google 推出）让网站管理员向爬虫提供正面信息（L7 p20 · L9 p11）：

  • 它们包含 URL 列表以及关于这些 URL 的数据，例如修改时间和修改频率。
  • 它们列在 robots.txt 中（CNN 的前六行，以 Sitemap: https://www.cnn.com/sitemaps/cnn/index.xml 开头）。
  • 它们由服务器管理员生成，通常通过脚本完成。
  • 它们可以告诉爬虫那些可能找不到的页面，即没有被任何页面链接的页面。
  • 它们给出页面的相对重要性，以及何时检查页面是否有变化的提示（更新频率）。

CNN 的 index.xml（L7 p22 · L6.5 p23）是一个 sitemap 索引：一个 <sitemapindex>，列出更多的 sitemap（video-2020-01.xml、article-2020-01.xml、…），每个都带有 <lastmod>。其中每一个（L7 p23 · L6.5 p24 · L9 p12）都是一个 <urlset>，每个页面对应一个 <url>：

<url>
  <loc>https://www.cnn.com/2012/01/25/world/gallery/wus-us-mia/index.html</loc>
  <lastmod>2012-01-25T18:24:37Z</lastmod>
  <changefreq>daily</changefreq>
  <priority>0.5</priority>
  <image:image>
    <image:loc>https://i2.cdn.turner.com/cnnnext/dam/assets/120111071718-jpac1-plane-story-top.jpg</image:loc>
    <image:caption>Gunnery Sgt. Bryon Bebout with the wreckage of a B-24 …</image:caption>
  </image:image>
</url>

<loc> = URL，<lastmod> = 修改时间，<changefreq> = 修改频率，<priority> = 相对重要性。箭头（L7 p23、L9 p12）标示的是 <lastmod> 和 <changefreq>，爬虫用它们来决定何时再次访问（第 8 节）。

4. 为什么基本算法不够用

基本算法在理论上是正确的，但在实践中严重不足（L7 p27–34，每帧一项）。它：

# 问题 参见
1 会惹恼网站管理员（不礼貌），它在滥用 Web 服务器 §5

5. 礼貌性与性能

5.1 礼貌性

避免过于频繁地访问任何网站：网站是为人服务的，而不是为机器人服务的（L7 p35）。如果忽视礼貌性，你的爬虫就是一次拒绝服务（DoS）攻击。要保持礼貌：对同一服务器的请求之间使用人为延迟。

5.2 性能：爬虫大部分时间在等待

获取一个页面需要经过多次网络往返（L9 p5）：

  1. 爬虫（一个客户端程序）连接到 域名系统（DNS） 服务器。
  2. DNS 将主机名转换为 IP 地址。
  3. 爬虫连接到服务器主机的特定 端口。
  4. 它发送一个 HTTP 请求 来获取该页面，通常是 GET。

粗略估算（L7 p36）：每次获取 500 毫秒，一次一个地抓取 100万个页面需要 500,000 秒，约 5.8 天，而且由于服务器无响应，实际情况“比这更糟”。大部分时间里线程都在等待网络数据。→ 例题 15.1

L9 p6–9 逐条列出了这一权衡：
问题 Web 爬虫花费大量时间等待请求的响应
解决方案 使用线程，一次获取数百个页面（或分布式地进行爬取，L7 p36）
缺点 爬虫可能会向网站泛滥请求
缓解措施 礼貌策略：例如把请求分散到不同服务器，对同一 Web 服务器的请求之间设置延迟，……

使用线程时，礼貌性更难控制，但仍然可以实现，例如让不同线程访问不同的服务器（L7 p36）。

在哪里执行礼貌策略？（L9 p10）“可以放在这里”：website ← frontier.nextSite()；“也可以放在这里”：url ← website.nextURL()。在演示中，每个主机在一次获取后必须休息 2 个 tick（时间刻）；nextSite() 会跳过正在休息的主机，当所有主机都在休息时，线程会等待：

5.3 DNS 查询

在任何获取之前，爬虫必须把域名转换为 IP 地址（L7 p37）：www.ics.uci.edu → 128.195.1.83。DNS 是一组分布式服务器：延迟可能很高（2 秒并不罕见），常见实现是阻塞式的（一次只处理一个请求），而且结果会被缓存。若每次查询需要 800 毫秒，查询整个 Web 需要多长时间？幻灯片没有给出主机数量；按每百万个域名计算，约为 9.3 天（每次 2 秒则约 23 天）。→ 例题 15.2

💡 关键洞见：爬虫是 I/O 密集型（I/O-bound） 的，在 Go 中使用 goroutine，在 Python 中使用线程或异步 I/O。按主机缓存 DNS 是最便宜的加速方法。

6. 爬虫陷阱

爬虫陷阱（crawler trap）可能会把爬虫永远困在一个站点上：Web 服务器返回不断变化的 URL 和内容，通常来自动态页面（L7 p38）。陷阱可以是：

  • 无意的：例如ICS 日历就是一个爬虫陷阱。每个月份页面都链接到下一个月份，永无止境。
  • 有意的：一些网站管理员设置陷阱来惩罚不礼貌的爬虫（fleiner.com/bots），例如非常大的文档，它们在 robots.txt 中被禁止，目的是消耗资源，或破坏忽略 robots.txt 的爬虫中设计不良的解析器。

演示中的日历总是链接到一个从未见过的 URL（?n=1、?n=2、…），因此已见集合永远不起作用，只有 10 次获取的预算能让它停下来：

{"title": "爬虫陷阱：ICS 日历（L7 p38）", "web": "www.ics.uci.edu/ -> www.ics.uci.edu/calendar, www.ics.uci.edu/about; www.ics.uci.edu/about -> www.ics.uci.edu/", "seeds": "www.ics.uci.edu/", "trap": "www.ics.uci.edu/calendar", "maxFetches": 10}

该站点只有 3 个真实页面，但 10 次获取中有 8 次都指向了日历，而待爬队列仍然没有清空。

⚠️ 易错点：有意设置的陷阱针对的是忽略 robots.txt 的爬虫。遵守 robots.txt 是第一道防线；限制每个主机的页面数量或 URL 深度，以及发现几乎相同的页面，可以捕获无意的陷阱。

7. 重复内容、数据噪声、客户端脚本与深网

重复内容（L7 p39）。完全重复和近似重复都非常普遍：副本、镜像站点、版本、垃圾信息、抄袭。研究发现 30% 的网页是其他 70% 的[近似]重复。它们几乎没有价值：对搜索引擎和用户来说都是噪声，用户应该只看到一份副本（也许附带一个“显示相似内容”的链接）。

完全重复 近似重复
检测方法 简单：哈希（hash）、校验和 较难：页面指纹（fingerprint）
常见程度 少见 常见

数据噪声（L7 p40–41 · L6.5 p26）。页面包含与页面内容无关的部分，例如广告、模板，而噪声会损害检索效果。截图中用方框标出了顶部横幅广告以及左右两栏。查找内容块的技术 1 是标签的累积分布（文档斜率曲线，Finn、Kushmerick 与 Smyth，2001）。图中 x 轴为词元（token）数量（0–3,500），y 轴为标签数量（0–900）。曲线在标签密集处上升，在“文本区域”（约 1,000–1,500 个词元）几乎变平，那里就是正文内容。文献中还存在其他技术。

客户端脚本（L7 p42–43）。现代网站大量使用脚本（JavaScript、TypeScript），内容隐藏在 XMLHttpRequest 之后。要获取这些内容，必须与脚本交互，即用户交互模拟（例如 Selenium），这很困难。大多数爬虫不会这样做，因此这些内容从未被索引。

深网（deep web）（L7 p44）是爬虫很少涉足的地方：隐藏在登录表单后的内容、隐藏在 JavaScript/TypeScript 后的内容，以及没有被任何地方链接的站点（站点地图有助于处理这些内容，第 3 节）。据估计，它的规模是浅网的 400–500 倍。

8. 何时重新爬取：新鲜度与年龄

8.1 新鲜度

页面会不断被添加、删除和修改（L9 p13）。过时的副本不再反映真实的页面，因此爬虫必须反复重新访问，以维持新鲜度（freshness）。HTTP 的 HEAD 请求返回的是页面的相关信息，而不是页面本身（L9 p14–15）：

Client request:  HEAD /csinfo/people.html HTTP/1.1
                 Host: www.cs.umass.edu

Server response: HTTP/1.1 200 OK
                 Date: Thu, 03 Apr 2008 05:17:54 GMT
                 Server: Apache/2.0.52 (CentOS)
                 Last-Modified: Fri, 04 Jan 2008 15:28:39 GMT
                 ETag: "239c33-2576-2a2837c0"
                 Accept-Ranges: bytes
                 Content-Length: 9590
                 Connection: close
                 Content-Type: text/html; charset=ISO-8859-1

箭头指向 Last-Modified：将它与你存储副本的日期进行比较。你可以自己试一试（L9 p15）：

curl --head https://www.ics.uci.edu/~algol/index.html

你无法持续检查每个页面，应该检查重要的和经常变化的页面（L9 p16）。新鲜度是集合中新鲜页面所占的比例，而优化它是危险的：一个总是在更新的站点，在你的副本中几乎永远不是新鲜的，因此一个以新鲜度最大化为目标的引擎会停止爬取它。另一个指标是年龄。

8.2 新鲜度与年龄

图（L9 p17 · L6.5 p31–32）在同一时间轴上展示：爬取、更新、爬取、更新、爬取。

事件 新鲜度 年龄
爬取 1（副本与页面一致） 0
爬取之后页面更新 降为 0 从 0 开始线性增长
下次爬取前又发生更新 保持为 0 继续增长（从第一次错过的变化开始计时）
下一次爬取 恢复为 1 恢复为 0

新鲜度是非真即假的阶跃；年龄衡量副本过时了多久。

8.3 期望年龄

页面在上次爬取后 ttt 天的期望年龄（L9 p18–20）：

Age(λ,t)=∫0tP(page changed at time x) (t−x) dx\text{Age}(\lambda, t) = \int_0^t P(\text{page changed at time } x)\,(t - x)\,dxAge(λ,t)=∫0t​P(page changed at time x)(t−x)dx

P(page changed at time x)P(\text{page changed at time } x)P(page changed at time x) 是页面在时刻 xxx 发生变化的概率；(t−x)(t - x)(t−x) 是该变化与现在之间的时间，即副本已经过时了多久（L9 p19）。平均而言，更新服从泊松过程（Poisson process）（Cho & Garcia-Molina，2003），因此到下一次更新的时间服从指数分布（exponential），其均值为变化频率 λ\lambdaλ（每天的变化次数）：

Age(λ,t)=∫0tλe−λx (t−x) dx=t−1−e−λtλ\text{Age}(\lambda, t) = \int_0^t \lambda e^{-\lambda x}\,(t - x)\,dx = t - \frac{1 - e^{-\lambda t}}{\lambda}Age(λ,t)=∫0t​λe−λx(t−x)dx=t−λ1−e−λt​

（闭式解是我推导的，已做数值检验。）L9 p21 对 λ=1/7\lambda = 1/7λ=1/7（每周一次变化）、ttt 从 0 到约 7 天的情况作图：曲线向上弯曲，t=2t = 2t=2 时为 0.26，t=4t = 4t=4 时为 0.95，t=6t = 6t=6 时为 1.97，t=7t = 7t=7 时为 7/e≈2.587/e \approx 2.587/e≈2.58。

💡 关键洞见：“页面越老，不去爬取它的代价就越大”（L9 p21）。期望年龄的增长快于线性，因此每多等一天的代价都比前一天更大，对 λ\lambdaλ 较大的页面来说更是如此。

9. 分布式爬取

使用多台计算机进行爬取有三个理由（L9 p22）：

  1. 它让爬虫更接近它所爬取的站点，从而降低网络需求。
  2. 它减少每个爬虫需要记住的站点数量，从而降低本地内存需求。
  3. 它总体上减少了本地所需的资源。

分布式爬虫可能会使用哈希函数，根据 URL 的主机部分把 URL 分配给计算机或线程。这样每个主机只由一个爬虫负责，从而能保持礼貌。L9 p23–24 展示了五次 CrawlerThread，每次都高亮了 (frontier)：边界信息应当共享（一个已见集合，一份礼貌性状态）。

10. 其他类型的爬取：聚焦爬取、桌面爬取、文档订阅源

聚焦爬取（focused crawling）（L9 p26）只下载与某个特定主题相关（或围绕特定时间事件）的页面，用于垂直搜索，或为某一主题改进搜索引擎。同一主题的页面倾向于链接到同一主题的页面。热门页面可以作为种子（例如用户搜索某个关键词后点击最多的页面），并由文本分类器判断页面是否属于该主题。

桌面爬取（desktop crawls）（L9 p27）用于桌面和企业搜索，与 Web 爬取不同：数据更容易找到（文件系统 ≈ 站点地图）；对更新做出快速响应更重要；它们必须节省磁盘、内存和 CPU（对用户透明）；必须处理多种文档格式；数据隐私也重要得多。

文档订阅源（document feed）（L9 p28–29）。许多文档只是被发布，即创建一次，很少更新，例如新闻、博客文章、新闻稿和电子邮件。来自同一来源的已发布文档形成一个序列，即文档订阅源；爬虫在订阅源的末尾寻找新文档。有两种类型：

  • 推送订阅源（push feed）会提醒订阅者有新文档，例如新闻社的订阅源。推送需要订阅，例如 WebSub。
  • 拉取订阅源（pull feed）要求订阅者定期检查新文档。最常见的拉取格式是 RSS，即 Really Simple Syndication / RDF Site Summary / Rich Site Summary。

RSS 示例（L9 p30–33）：

<?xml version="1.0"?>
<rss version="2.0">
  <channel>
    <title>Search Engine News</title>
    <link>http://www.search-engine-news.org/</link>
    <description>News about search engines.</description>
    <language>en-us</language>
    <pubDate>Tue, 19 Jun 2008 05:17:00 GMT</pubDate>
    <ttl>60</ttl>

    <item>
      <title>Upcoming SIGIR Conference</title>
      <link>http://www.sigir.org/conference</link>
      <description>The annual SIGIR conference is coming!
        Mark your calendars and check for cheap
        flights.</description>
      <pubDate>Tue, 05 Jun 2008 09:50:11 GMT</pubDate>
      <guid>http://search-engine-news.org#500</guid>
    </item>
    ...
    <item>
      <title>New Search Engine Textbook</title>
      <link>http://www.cs.umass.edu/search-book</link>
      <description>A new textbook about search engines
        will be published soon.</description>
      <pubDate>Tue, 05 Jun 2008 09:33:01 GMT</pubDate>
      <guid>http://search-engine-news.org#499</guid>
    </item>

</rss>

第一个 <item> 之前是订阅源频道信息，每个 <item> 是条目信息（L9 p31）；箭头（p32–33）标出了 <pubDate> 和 <ttl>。对爬虫来说（L9 p34）：

  • <ttl>（存活时间）是内容应被缓存的时长，单位为分钟，这里是 60。
  • 订阅源像网页一样通过 HTTP GET 访问；使用 HEAD 来检查订阅源是否有变化。
  • 订阅源很容易解析（它就是 XML），新信息也很容易找到：GET、解析，然后取出任何新的 <item> … </item> 条目。

13. 版权、合理使用与法律案例

版权（L8 p19–20）。智力成果，例如 Web 内容和源代码，受版权法保护：这是一种“以美国宪法为基础、由法律授予的保护，适用于以有形媒介固定的原创作品”，无论是否发表（copyright.gov）。那么你能使用网络上的材料吗？

合理使用（fair use）（L8 p21–22）。为批评、评论、新闻、教学、学术和研究等目的进行复制，可能被视为合理使用，但这是一个非常模糊的领域。有四个因素决定某一具体使用是否合理：

  1. 使用的目的和性质，包括是否具有商业性，或是否为非营利的教育目的。
  2. 受版权保护作品的性质。
  3. 所使用部分的数量和实质性，相对于作品整体而言。
  4. 对作品潜在市场或价值的影响。

法律案例（L8 p23–24）。两起案件都是依据“侵占动产（trespass to chattels）”获胜的，即干扰他人的财产，这里指他们的计算机系统。

案件 日期 发生了什么 裁决
eBay vs. Bidder's Edge 2000年5月24日 eBay 阻止了 Bidder's Edge 的爬虫 故意、未经授权地干扰 eBay 的计算机系统，并造成损害
American Airlines vs. FareChase 2003年3月10日 AA 阻止 FareChase 抓取 AA.com 的“web fares”（票价比较） 故意、未经同意；损害了 AA 的网络和财产。同年晚些时候达成和解

更多内容可参阅 UCI 的计算机法研究生课程（L8 p25）。

⚠️ 易错点：两起案件都与爬取有关（对服务器的负载，以及未经授权使用服务器），而不是复制文本。遵守 robots.txt 和礼貌性规则，不仅是良好的礼仪，也是法律层面的要求。

15. 示例题（附解答）

15.1 爬取100万个网页的时间（L7 p36）

获取一个页面需要 500 毫秒。一次一个地爬取 100万个页面需要多长时间？使用线程后会有什么变化？

✍️ 先自己试一试。

解答。 106×0.5 s=500,000 s10^6 \times 0.5\ \text{s} = 500{,}000\ \text{s}106×0.5 s=500,000 s ≈ 138.9 小时 ≈ 5.8 天，实际上更糟（服务器无响应），而且几乎全部时间都在等待网络。若使用 kkk 个线程并行（分布在不同服务器上以保持礼貌），理想时间为 500,000/k500{,}000 / k500,000/k 秒：10 个线程约 13.9 小时，100 个约 1.4 小时，500 个约 17 分钟。返回 第 5.2 节。

15.2 DNS 查询耗时800毫秒（L7 p37）

一次 DNS 查询需要 800 毫秒，常见的解析器是阻塞式的（一次只处理一个请求）。“查询整个 Web”需要多长时间？

✍️ 先自己试一试。

解答。 没有给出主机数量，因此按每 100万个域名计算：106×0.8 s=800,000 s≈9.310^6 \times 0.8\ \text{s} = 800{,}000\ \text{s} \approx 9.3106×0.8 s=800,000 s≈9.3 天；若每次 2 秒，约为 23 天。解决办法：缓存（一次查询可以服务于某个主机的所有 URL），并且不要阻塞，即并发地解析。返回 第 5.3 节。

15.3 哪条 robots.txt 规则适用？（L7 p18 · L6.5 p16–21）

对 L7 p18 表格中的每个文件，BadBot、Google 和 MyCrawler 是否可以获取 /、/tmp/a.html 和 /index.html？

✍️ 先自己试一试。

解答。 首先选择分组（指名该机器人的分组优先于 *），然后匹配路径。这些结果已用 Python 的 urllib.robotparser 验证：

文件 BadBot Google MyCrawler
全部禁止（*：Disallow: /） 无 无 无
全部允许（*：Disallow:） 全部 全部 全部
部分禁止（*：/cgi-bin/、/tmp/、/junk/） /、/index.html（不含 /tmp/a.html） 同上 同上
禁止单个机器人（BadBot：Disallow: /） 无 全部（无分组适用） 全部
允许单个机器人（Google：Disallow: + *：Disallow: /） 无 全部 无

最后一行正是优先级规则：Google 自己的分组允许一切，* 分组对它不适用。核对：

{"title": "允许单个机器人 + 优先级规则（L7 p18 · L6.5 p21）", "robots": "User-agent: Google\nDisallow:\n\nUser-agent: *\nDisallow: /", "urls": "/index.html, /tmp/a.html", "agent": "Google"}

（robotparser 会把分组名作为子串匹配，因此 Googlebot/2.1 也会匹配 Google 分组；RFC 9309 要求精确匹配令牌。）返回 第 2 节。

15.4 允许规则位于被禁止的文件夹内（L7 p24）

CNN 的规则为 Allow: /audio/podcasts/、Allow: /partners/ipad/live-video.json、Disallow: /audio/ 和 Disallow: /partners/。判断 /audio/podcasts/ep1.mp3、/audio/live.html、/partners/ipad/live-video.json 和 /partners/ipad/x.json 是否允许访问。

✍️ 先自己试一试。

解答。 找出路径是 URL 路径前缀的每一条规则，让最长的那条获胜：

路径 匹配的规则 胜出者 结论
/audio/podcasts/ep1.mp3 Allow: /audio/podcasts/（16）、Disallow: /audio/（7） Allow 允许
/audio/live.html Disallow: /audio/ Disallow 禁止
/partners/ipad/live-video.json Allow: …/live-video.json（30）、Disallow: /partners/（10） Allow 允许
/partners/ipad/x.json Disallow: /partners/ Disallow 禁止

被禁止的文件夹是关闭的，只有网站希望被爬取的资源例外。只有因为 CNN 把 Allow 行放在最前面，“先匹配者胜出”的规则才会得出相同的答案。返回 第 2 节。

字段 值

15.6 每周变化一次时的期望年龄（L9 p18–21）

若 λ=1/7\lambda = 1/7λ=1/7（每天的变化次数），页面在爬取后 2、4、6 和 7 天的期望年龄分别是多少？

解答。 对 λe−λx(t−x)\lambda e^{-\lambda x}(t - x)λe−λx(t−x) 从 0 积分到 ttt，得到 Age(λ,t)=t−(1−e−λt)/λ\text{Age}(\lambda, t) = t - (1 - e^{-\lambda t})/\lambdaAge(λ,t)=t−(1−e−λt)/λ：

ttt（天） 1 2 4 6 7
期望年龄（天） 0.07 0.26 0.95 1.97 2.58

这与 L9 p21 的曲线相符（右端约 2.5，向上弯曲）；在 t=7t = 7t=7 时，年龄恰好为 7e−17e^{-1}7e−1。从第 4 天到第 6 天增加了约 1 天的期望年龄，从第 0 天到第 2 天只增加了约 0.26。返回 第 8 节。

16. 速查与必记的 5 个要点

robots.txt 含义
User-agent: Name 针对该机器人的分组；如果存在，则只有它的规则适用于该机器人（L6.5 p21）
Disallow: / / Disallow: 禁止一切 / 不禁止任何内容
Disallow: /tmp/ 禁止以 /tmp/ 开头的路径
Disallow: /audio/ 下的 Allow: /audio/podcasts/ 在关闭的文件夹中重新开放一个资源（最长匹配获胜）
Sitemap: URL 站点地图的位置
爬虫问题（L7 p27–34） 幻灯片中的解决方法
不礼貌 按主机设置人为延迟；在 nextSite() / nextURL() 中执行
慢（等待网络和 DNS） 线程 / 分布式爬取；缓存 DNS
陷阱 遵守 robots.txt；注意不断变化的 URL（例如 ICS 日历）
重复内容 哈希/校验和（完全重复）、指纹（近似重复）
噪声 内容块：标签累积分布
客户端脚本 用户交互模拟（Selenium），大多数爬虫会跳过它
术语 含义
待爬队列 等待爬取的 URL 队列，从种子开始
HEAD 只请求头部信息的 HTTP 请求（Last-Modified）
新鲜度 集合中保持最新的比例
年龄 副本已经过时多久；Age(λ,t)=∫0tλe−λx(t−x) dx\text{Age}(\lambda,t) = \int_0^t \lambda e^{-\lambda x}(t-x)\,dxAge(λ,t)=∫0t​λe−λx(t−x)dx
分布式爬取 对主机做哈希，分配给爬虫；共享待爬队列
推送 / 拉取订阅源 发布者提醒你（WebSub）/ 你轮询（RSS，<ttl> 以分钟计）
深网 隐藏在登录、脚本之后或未被链接；是浅网的 400–500 倍
侵占动产 eBay v. Bidder's Edge 与 AA v. FareChase 案的诉由（trespass to chattels）

必记的 5 个要点

  1. 爬取循环：待爬队列 → 是否允许？ → 获取 → 存储 → 提取 → 加入未见过的链接；礼貌性位于 nextSite()/nextURL() 中。
  2. robots.txt：针对特定机器人的分组会完全覆盖 *；在被 Disallow 的文件夹中，Allow 通过最长匹配获胜；它基于君子协定，不是安全机制。
  3. 爬取是 I/O 密集型的：100万个页面 × 500 毫秒 ≈ 单线程下 5.8 天，因此要使用多个线程，并且对每个主机保持礼貌。
  4. 优化新鲜度可能会让你放弃变化快速的站点；年龄随着自上次爬取以来的时间增长，且增长快于线性。
  5. “你能做，不代表你就该做”：遵循机器人编写者指南，标识你的机器人，并记住两起法律案例都与爬取有关（侵占动产）。
