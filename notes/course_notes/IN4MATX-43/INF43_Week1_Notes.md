## 一、软件无处不在

课程首先通过大量真实案例说明：软件已经**渗透到社会的每一个角落**，影响深远且不可忽视。

| 领域 | 具体案例 |
|------|----------|
| **汽车** | Two-Mode Hybrid 变速箱项目中，约 **70% 的工时**用于开发控制软件——软件已成为汽车工程的核心 |
| **医疗** | Epic 电子健康记录系统（EHR）部署成本惊人：Duke 大学 7 亿美元，UC 系统 1.5 亿美元 |
| **政治** | 研究表明搜索引擎排名越高的政客，越可能获得选票——软件在暗中影响民主决策 |
| **军事** | 海军开发"Pirate Predictor"算法，结合情报和环境条件建模预测海盗行为 |
| **太空** | 航天任务严重依赖软件控制系统 |
| **灾害响应** | 软件在灾难救援协调中发挥关键作用 |
| **游戏** | 2018 年视频游戏行业收入达 **438 亿美元**（Fortnite、Call of Duty 等驱动） |
| **执法** | 软件用于嫌疑人追踪和定位 |

**关键总结**——软件的双面性：

- ✅ 令人兴奋的、多用途的、可以拯救生命、帮助人们
- ❌ 也可以**伤害人们**

> **引出核心问题**：既然软件如此重要且无处不在，那么这些软件是**如何被制造出来的**？→ 这就是软件工程要回答的问题。

## 二、什么是软件工程？——定义

### 2.1 "软件"不仅仅是代码

**Software（软件）** 包含：
- **代码**（Code）
- **文档**和用户手册（Documentation, User Manuals）
- **设计和规格说明**（Designs, Specifications）
- **测试用例**（Test Cases）
- **计划和进度表**（Plans and Schedules）

**Engineering（工程）** 的含义：
- 创造性地应用科学和数学来**设计和构建**事物
- 涉及**权衡取舍（trade-offs）**、**风险分析**、技能和知识

### 2.2 专家定义对比

| 来源 | 定义 | 强调的关键点 |
|------|------|-------------|
| **Tsui, Karam, Bernal** | "一个涉及软件系统开发和支持**所有方面**的广泛领域" | **广泛性**：不只是编码，涵盖开发到维护的全链条 |
| **Ghezzi, Jazayeri, Mandrioli** | "处理**如此大型**的软件系统构建的学科，以至于需要**一个或多个工程师团队**来完成" | **规模**和**团队协作** |
| **Parnas** | "**多人**构建**多版本**软件" | 最精炼的定义：**多人协作** + **多版本迭代** |
| **Schach** | "旨在生产**无故障**软件的学科，**按时交付**且**在预算内**，满足用户需求。软件还必须在用户需求变化时**易于修改**" | **质量**、**时间**、**成本**、**可维护性**——最全面 |

### 2.3 INF 43 课程定义（重点！）

本课程将软件工程定义为**三大支柱**：

1. **构建软件的过程**（The process of constructing software）
2. **编程之外的开发阶段**（Phases of development other than programming）
   - 需求、设计、测试、部署、维护……编码只是其中一环
3. **具有持久价值的原则和质量**（Principles and qualities of enduring value）
   - 例如：**正确性（Correctness）**、**效率（Efficiency）**、**健壮性（Robustness）**

次要关注点：团队管理与调度、商业模式、软件对社会的影响、AI

## 三、三种视角看软件工程

课程通过三个虚构人物展示不同**利益相关者**如何看待同一款软件：

| 人物 | 身份 | 视角名称 | 关注什么 | 软件工程如何帮助？ |
|------|------|----------|----------|-------------------|
| **Shawna** | CEO | **商业视角（Business）** | 成本、利润、投资回报、市场规模 | 控制开发成本，按时交付，创造商业价值 |
| **Andy** | 软件工程师 | **工程视角（Engineering）** | 技术实现、系统可靠性、代码质量、性能 | 提供系统化方法和工具来构建可靠的软件 |
| **Clara** | 在职母亲 | **用户视角（User）** | 用户体验、界面美观度、易用性、趣味性 | 以用户为中心的设计，确保产品真正满足需求 |

**更多视角**：

- **程序员** → 源代码、内部设计
- **电气工程师** → 半导体、晶体管、电源
- **社会** → 影响、输出、趋势、危险
- **设计师** → 产品、结构
- **项目经理** → 团队、预算、时间表
- **SE 教授** → 原则、理论、模型
- **SE 学生** → 工作量、机遇、挑战、乐趣

> **核心启示**：同一款软件，不同角色的人"看到"的东西完全不同。软件工程需要**同时兼顾多方利益相关者的需求**。

## 四、软件工程的三大核心要素

$$\boxed{\text{People（人）} + \text{Processes（过程）} + \text{Tools（工具）}}$$

这是贯穿整个课程的**根基概念**：
- **People**：软件是由人构建的，人的能力、沟通和协作是成功的关键
- **Processes**：需要系统化的流程来组织和管理开发活动
- **Tools**：工具（IDE、版本控制、测试框架等）提升效率，但工具本身不能替代人和过程

## 五、软件工程原则

### 5.1 不同学者的原则总结

**Davis (1994)**：
- 质量第一
- 尽早给客户交付产品
- **先理解问题**再动手
- 选择合适的过程
- 好的管理比好的技术更重要
- **人是成功的关键**

**Royce (1998)**：
- 遵循**架构优先**的过程
- **基于组件的开发**（Buy vs. Build）减少编码量
- 频繁向客户展示初步版本
- **增量式发布**

**Wasserman (1996)**：
- 模块化（Modularity）
- 抽象（Abstraction）
- 用户界面原型（UI Prototyping）
- 复用（Reuse）
- 度量（Metrics）

### 5.2 INF 43 课程核心原则（必须掌握！）

| 原则 | 含义 |
|------|------|
| **Rigor and Formality（严格性与形式化）** | 用严谨、系统的方法取代随意的做法；使用形式化的表示法和方法论 |
| **Separation of Concerns（关注点分离）** | 将复杂问题分解为更小、更易管理的部分，下含三个子原则 ↓ |
| → **Modularity（模块化）** | 将系统分解为独立的模块，每个模块有明确的职责 |
| → **Divide and Conquer（分而治之）** | 将大问题拆分为小问题逐个解决 |
| → **Abstraction（抽象）** | 隐藏不必要的细节，只暴露关键信息 |
| **Anticipation of Change（对变化的预见）** | 设计时就考虑到未来的变更需求，使软件更易于修改 |
| **Generality（通用性）** | 尽可能设计通用的解决方案，而非针对单一特定问题 |
| **Incrementality（增量性）** | 逐步构建，每次增加一点功能，而非试图一次完成所有内容 |

## 六、No Silver Bullet — Brooks (1986)

### 6.1 文章背景

- **作者**：Frederick Brooks，图灵奖得主
- **发表**：1986 年
- **地位**：软件工程领域的**奠基性文章（seminal article）**，至今几乎每位软件工程师都知道
- **核心论点**：不存在能使软件开发生产力在十年内提升一个数量级的"银弹"（单一技术或方法）

### 6.2 软件的四大本质属性（Essential Properties）

这是 Brooks 论证"没有银弹"的基础——软件的困难来自其**本质（essence）**，而非偶然因素（accidents）：

| 本质属性 | 含义 | 深层解释 |
|----------|------|----------|
| **Complexity（复杂性）** | 软件由相互交织的概念构成：数据结构、类、算法、函数调用 | "没有两个部分是相同的"——不像物理制造可以大量复制，软件的每个部分都是独特的，导致指数级增长的复杂度 |
| **Conformity（一致性/顺从性）** | 软件必须**顺应**人类已有的制度和系统 | 法规、标准、遗留系统、组织流程——这些外部约束不是软件设计者能控制的，却必须去适配 |
| **Changeability（可变性）** | "所有成功的软件都会被修改" | 成功带来更多用户 → 更多需求；运行环境变化、硬件升级、法规更新——变化是不可避免的 |
| **Invisibility（不可见性）** | "软件的现实并非天然嵌入空间中" | 软件没有物理形态，不像建筑有蓝图可以直观展示；难以可视化全貌，增加了理解和沟通的难度 |

### 6.3 "虚假的"银弹（False Silver Bullets）

Brooks 逐一分析了当时被寄予厚望的技术，认为它们**有帮助但都不能从根本上解决问题**：

- 高级语言（High-level languages）
- 分时系统（Time-sharing）
- 统一编程环境（Unified programming environments）
- 面向对象编程（OOP）
- 人工智能（AI）
- 专家系统（Expert systems）
- 自动/图形化编程（Automatic/graphical programming）
- 程序验证（Program verification）
- 环境/工具（Environments/tools）
- 工作站（Workstations）

> 这些技术解决的是软件的**偶然困难（accidental difficulties）**，而非**本质困难（essential difficulties）**。这是文章标题中 "Essence and Accidents" 的核心含义。

### 6.4 "潜在的"银弹（可能大有帮助的方向）

虽然也不是真正的银弹，但 Brooks 认为以下方向**最有可能显著改善**软件开发：

| 方向 | 为什么有潜力 |
|------|-------------|
| **Buy vs. Build（购买 vs. 自建）** | 复用已有的高质量组件，避免重复造轮子 |
| **Requirements refinement + rapid prototyping（需求细化 + 快速原型）** | 尽早发现和纠正需求错误——需求错误是最昂贵的错误 |
| **Incremental development（增量式开发）** | 逐步构建、逐步反馈，降低风险 |
| **Great designers（优秀的设计师）** | 顶尖设计师和普通设计师的差距是巨大的——人的因素至关重要 |

## 七、课程核心问题与学习成果

### 7.1 贯穿课程的"大问题"

| 问题 | 对应主题 |
|------|----------|
| 我们如何知道该构建什么？ | **需求工程（Requirements Engineering）** |
| 我们如何组织软件结构？ | **软件架构（Software Architecture）** |
| 我们如何设计软件细节？ | **设计、模型、符号（Designs, Models, Notations）** |
| 我们如何使软件满足用户需求？ | **用户导向（User Orientation）** |
| 我们如何知道软件是否正确工作？ | **测试（Testing）** |
| 我们遵循什么流程来开发？ | **软件过程模型（Software Process Models）** |

### 7.2 学习成果

完成课程后应能做到：
- 描述 SE 基本原则
- 创建**需求文档**和**用例模型**
- 描述软件架构及不同**架构风格**
- 创建 **UML 类图**
- 创建**黑盒测试计划**和**白盒测试**（不同覆盖标准）
- 描述不同**软件过程模型**
- 识别良好**用户导向**的原则与实践

### 一句话总结

> 软件工程不仅仅是编程——它是**人、过程和工具**的结合，通过**系统化的原则**来应对软件固有的**复杂性、一致性、可变性和不可见性**，从而在多方利益相关者的视角下构建高质量软件。
